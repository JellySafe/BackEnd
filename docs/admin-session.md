# 관리자 세션 — 쿠키로 옮긴 이유와 계약

> 이슈 [#55](https://github.com/JellySafe/BackEnd/issues/55) 결정 기록.
> 프론트가 Next middleware 로 **서버에서** 세션을 검증할 근거가 되는 문서다.

---

## 1. 무엇이 문제였나

관리자 앱은 `accessToken` 을 `sessionStorage` 에 평문으로 들고 있었다. 서버가 그렇게 만들었기
때문이다 — `POST /admin/auth/login` 이 토큰을 **응답 본문으로만** 돌려줬으므로, 브라우저가
자동으로 실을 방법이 없었고 프론트는 JS 로 보관할 수밖에 없었다.

그 상태에서 XSS 가 한 번 나면 **위험도 발표와 주민 대상 알림 발송 권한이 그대로 나간다.**
일반적인 관리 도구보다 유출 비용이 크다. 그리고 라우트 가드가 클라이언트 전용이라 우회도
가능했는데, 서버 검증을 붙이려 해도 **middleware 가 읽을 쿠키가 없었다.**

---

## 2. 결정 — 쿠키와 헤더를 **병행**한다

세션을 `httpOnly` 쿠키로 내려준다. 동시에 **응답 본문의 토큰과 `Authorization: Bearer` 인증을
그대로 남긴다.** 한쪽으로 강제하지 않은 이유는 쓰는 쪽이 다르기 때문이다.

| 호출자 | 인증 방법 | 이유 |
|---|---|---|
| 관리자 웹(브라우저) | **쿠키** | JS 가 토큰을 만지지 않는다 → XSS 로 유출되지 않는다 |
| Swagger UI | Bearer | Authorize 버튼 흐름이 그대로 살아 있어야 한다 |
| 운영 스크립트·서버 간 호출 | Bearer | 쿠키 저장소가 없는 호출자다 |

**헤더가 쿠키보다 우선한다.** 둘 다 있으면 헤더를 쓴다 — 호출자가 명시한 값이고, 브라우저에
남아 있는 쿠키가 그 의도를 덮으면 다른 계정으로 시험하려던 요청이 조용히 엉뚱한 세션을 탄다.

> 응답 본문에 토큰이 아직 남아 있는 것은 위 두 호출자 때문이다.
> **관리자 웹은 그 값을 저장하지 않는다.** 저장하는 순간 쿠키로 옮긴 의미가 사라진다.

---

## 3. 쿠키 세 개

| 이름 | httpOnly | 경로 | 수명 | 용도 |
|---|---|---|---|---|
| `js_access_token` | ✅ | `/` | `JWT_EXPIRES`(기본 30m) | 모든 `/admin/*` 요청 인증 |
| `js_refresh_token` | ✅ | `{prefix}/admin/auth` | `REFRESH_TOKEN_EXPIRES_DAYS`(기본 14일) | 재발급·로그아웃 |
| `js_csrf_token` | ❌ **일부러** | `/` | 리프레시와 동일 | 프론트가 읽어 헤더로 되돌린다 |

공통 속성: `SameSite=Lax`, `Secure`(운영만 — 로컬 http 에서 붙이면 브라우저가 쿠키를 버린다).

**왜 이렇게 두었나**

- **리프레시 쿠키의 경로를 좁힌 것** — 모든 요청에 딸려 다닐 이유가 없다. 경로를 좁히면 그 값이
  오가는 요청 수가 줄고 로그·프록시에 노출될 표면도 줄어든다.
- **CSRF 쿠키만 httpOnly 가 아닌 것** — 프론트가 읽어야 하기 때문이다. 노출돼도 괜찮은 이유는
  **공격자 사이트가 다른 오리진의 쿠키를 읽지 못하기** 때문이다. 즉 헤더에 실을 값을 알 수 없다.
- **CSRF 쿠키가 리프레시만큼 오래 사는 것** — 액세스 토큰과 같이 죽으면, 만료된 뒤 재발급을
  부르는 바로 그 순간에 CSRF 토큰이 없어 재발급이 막힌다.
- **`SameSite=Strict` 가 아닌 것** — Strict 는 다른 사이트에서 관리자 콘솔 링크를 눌러 들어올 때
  첫 이동에 쿠키를 싣지 않는다. 메신저로 받은 링크를 눌렀을 뿐인데 로그아웃된 것처럼 보인다.
  Lax 도 크로스 사이트 **상태 변경 요청**에는 쿠키를 싣지 않으므로 방어의 핵심은 유지된다.

## 4. CSRF — 쿠키 전환이 데려온 대가

Bearer 헤더 방식에는 CSRF 가 없었다. 공격자가 남의 브라우저에 임의 헤더를 붙일 수 없기
때문이다. 쿠키로 옮기면 **브라우저가 알아서 실어 준다.** 다른 사이트의 폼 하나가
`POST /api/admin/notifications/send` 를 쏘면 운영자 권한으로 주민에게 알림이 나갈 수 있다.

같이 막지 않으면 **XSS 를 막고 CSRF 를 여는 맞바꾸기**가 된다.

### 규칙

```
검사한다   : 쿠키로 인증한 POST / PUT / PATCH / DELETE
검사 안 한다: GET·HEAD·OPTIONS
             Authorization: Bearer 가 실린 요청   ← 기존 호출자가 그대로 동작하는 지점
             세션 쿠키가 아예 없는 요청
             POST /admin/auth/login (@NoCsrf)
```

프론트가 할 일은 하나다 — **`js_csrf_token` 쿠키를 읽어 `x-csrf-token` 헤더에 실는다.**
빠지면 `403 CSRF_TOKEN_INVALID`.

**로그인을 면제한 이유** — CSRF 가드는 세션 쿠키가 있으면 토큰을 요구한다. 어떤 이유로든 CSRF
쿠키만 사라지고 세션 쿠키가 남으면 **로그인조차 403 이 되어 스스로 빠져나올 수 없다.** 로그인은
복구 경로이므로 잠기면 안 된다. 남는 위험(공격자 계정으로 로그인시키는 login CSRF)은 관리자
콘솔에서 다른 이름·역할로 보여 곧 드러나고, `SameSite=Lax` 가 이미 크로스 사이트 POST 를 막는다.

## 5. CORS — 운영에서 `CORS_ORIGIN` 이 필수가 됐다

이 설정의 성격이 바뀌었다. 예전에는 미지정 시 모든 오리진을 허용해도 큰 문제가 아니었다 —
자격증명이 헤더에 있어 공격자 사이트는 인증된 요청을 만들 수 없었다. **쿠키에서는 전제가
뒤집힌다.** 브라우저가 쿠키를 자동으로 실어 주므로, 모두 허용한 채로 뜨면 아무 웹사이트나
로그인한 운영자 권한으로 관리자 API 를 부르고 **응답까지 읽을 수 있다.**

그래서 **운영에서 `CORS_ORIGIN` 이 비어 있으면 기동을 막는다.** 통과시키고 경고만 남기는
선택도 있지만, 그 경고는 아무도 보지 않는 사이 계속 열려 있게 된다. 설정 하나를 빠뜨린 배포가
실패하는 쪽이, 조용히 열린 채 뜨는 쪽보다 낫다(`SYSTEM_API_KEY` 와 같은 기준이다).

개발·테스트는 그대로 둔다 — localhost 포트가 계속 바뀌고, 그 환경에는 지킬 자료가 없다.

프론트가 Next rewrites 로 same-origin 프록시를 타면 애초에 CORS 를 거치지 않으므로 이 설정과
무관하게 동작한다. 쿠키 도메인도 어긋나지 않는다(같은 오리진이다).

## 6. 프론트가 붙일 middleware

```ts
// middleware.ts
export async function middleware(req: NextRequest) {
  const res = await fetch(new URL('/api/admin/auth/session', API_BASE), {
    headers: { cookie: req.headers.get('cookie') ?? '' },
  });
  if (!res.ok) return NextResponse.redirect(new URL('/login', req.url));
  return NextResponse.next();
}
```

`GET /admin/auth/session` 은 **상태 코드 하나로 판단이 끝나게** 만들었다. 200 이면 유효한 세션,
401 이면 로그인으로 보낸다. 본문에는 `userId` / `email` / `role` 과 `authVia` 가 담긴다.

`authVia` 는 전환 확인용이다. `cookie` 가 나와야 정상이고, **`bearer` 가 나오면 아직 JS 가 토큰을
들고 있다는 뜻**이다 — 그 코드가 남아 있는 것이다.

## 7. 남아 있는 한계 — 액세스 토큰은 여전히 취소할 수 없다

쿠키로 옮겨도 이 성질은 **그대로다.** JWT 는 서명만으로 검증되므로 서버가 발급된 토큰을 되돌릴
수단이 없다. 로그아웃도, 계정 정지도, 유출 인지도 남은 수명을 앞당기지 못한다.

바뀐 것은 하나다 — 로그아웃이 쿠키를 지우므로 **그 브라우저는** 더 이상 토큰을 싣지 않는다.
훔쳐 간 쪽에는 아무 영향이 없다.

그래서 수명을 짧게 두고(기본 30분, 운영 상한 2시간 — `shared/config/duration.ts`) 갱신을 쿠키로
돈다. 즉시성이 필요한 상황(기기 분실·유출)에는 `logout` 의 `allDevices: true` 로 그 계정의 모든
사슬을 끊어 **재발급을 막는다.** 남은 30분은 감수하는 값이다.

토큰을 즉시 취소하려면 서버가 상태를 들고 있어야 한다(블랙리스트 또는 세션 테이블). 그건
모든 요청에 조회를 하나 더 붙이는 일이라, 지금 규모에서 치를 값은 아니라고 봤다.

## 8. 마이그레이션 — 프론트가 지울 코드

이 이슈가 해결되면서 사라져야 하는 것들이다.

- `sessionStorage` 에 `accessToken` / `refreshToken` 을 넣고 빼는 코드 전부
- 요청마다 `Authorization` 헤더를 붙이는 인터셉터 (쿠키가 대신한다)
- `apps/admin/src/features/admin-auth/api/signOut.ts` 의 임시 조치 주석
  — 로그아웃은 이제 본문 없이 `POST /admin/auth/logout` 만 부르면 된다(쿠키에서 읽는다)

**새로 붙일 것**은 둘이다.

1. fetch 에 `credentials: 'include'` (same-origin 프록시면 `'same-origin'`)
2. 상태 변경 요청에 `x-csrf-token` 헤더 (`js_csrf_token` 쿠키 값)

서버는 두 방식을 모두 받으므로 **한 번에 갈아엎지 않아도 된다.** 화면 단위로 옮기고,
`GET /admin/auth/session` 의 `authVia` 로 각 화면이 어느 쪽을 타는지 확인하면 된다.

# 위험도 점수표 백테스트

> **이 문서 이후에 일어난 일** — 여기 실린 진단을 근거로 점수표를 개정했다.
> **결정 과정·최종 점수표·한계는 [`risk-rules-v2.md`](./risk-rules-v2.md) 를 보라.** 이 문서는 그 근거가 된 **측정 기록**이다.
> 아래 §3 의 "제안" 은 v2 확정 과정에서 **일부 뒤집혔다**(특히 파고·풍향 제거 → 5점 유지). §6 에 결과를 요약했다.

**결론부터**: 현행 점수표는 **실제 배포 상태(v1-as-run)에서 고밀도 해파리 출현을 단 한 번도 위험(danger) 단계로 잡아내지 못한다(재현율 0%).** 구현 버그로 두 룰이 죽어 있어 점수가 40점을 넘지 못하기 때문이다. 버그를 고쳐도(v1), 룰 점수(AUC 0.783)는 **"직전 주 NIFS 보고서를 그대로 베끼는" 무지성 베이스라인(AUC 0.823)보다 나쁘다.** 지금의 점수표는 심사에서 방어할 수 없다.

- 재현 스크립트: [`Backend/scripts/backtest-risk.ts`](../scripts/backtest-risk.ts)
- 실행: `npx ts-node --transpile-only -r tsconfig-paths/register scripts/backtest-risk.ts`
  (캐시가 있으면 `BACKTEST_NO_FETCH=1` 로 네트워크 없이 수 초 만에 재현된다)
- 실행일: 2026-07-14 (v2 확정 재실행 포함)

## 1. 방법론

### 1.1 정답 (ground truth)

**국립수산과학원(NIFS) 해파리 모니터링 주간보고**.

| 항목 | 값 |
|---|---|
| 목록 API | `OpenAPI_json?id=jellyList&gbn=0`, 2024-01-01 ~ 2026-07-14 |
| 목록상 주간보고 | **80건** |
| PDF 본문 파싱 성공 | **68건** (2024-05-09 ~ 2026-07-09) |
| 파싱 실패 | 12건 (첨부 PDF 없음 / 텍스트 추출 불가) |

주간보고 PDF(`jellyDetail` → `item2[0].board_file`)에서 기존 프로덕션 파서
[`nifs-report.parser.ts`](../src/contexts/observation/adapter/out/collector/nifs-report.parser.ts)를 **그대로 재사용**해
시군구(제주시/서귀포시)별 고밀도/저밀도 출현, 제주 출현률(붙임3), 특보 단계를 뽑았다. 파서는 새로 짜지 않았다.

### 1.2 입력 (features)

**기상청 API 허브 해양기상관측** `sea_obs.php` — `tm=` 에 과거 시각을 넣어 조회.
파싱은 프로덕션의 `parseSeaObs`([`kma-sea-obs.collector.ts`](../src/contexts/observation/adapter/out/collector/kma-sea-obs.collector.ts))를 그대로 호출했다(결측 `-99` → `null`).

- 해변 12곳 → `haversineKm` 최근접 관측소(SYS-002 `map-stations.service.ts` 와 동일 로직), 유형별 상위 2곳.
- 실제 조회 지점 12곳, 표본 시각 **KST 매일 12:00**, 총 **5,796 (지점 × 날짜)** 조회 (로컬 캐시).
- 결정 시점 = 각 조사 주의 **마지막 날 12:00 KST**. 그 시점에서 최근 3일 수온(TEMP_UP), 7일 평균 수온(TEMP_7D_AVG), 파고, 풍향·풍속을 구성.

### 1.3 예측 (prediction)

**프로덕션 도메인 코드를 그대로 호출했다. 엔진을 재구현하지 않았다.**

```
evaluateRiskVariables → evaluateReportWeights → deriveMinLevelTriggers
→ deriveConfidence → applyHorizon('now') → RiskEngine.calculate
```

점수표는 `DEFAULT_RULE_SCORES`(= `seed.ts` 의 `seedRiskRules()` 값), 윈도우는 `calculate-risk.service.ts` 의 `COLLECT_OPTIONS` 를 그대로 썼다.

### 1.4 라벨 누출(leakage) 차단

`NEARBY_ALERT` 는 `nearbyWindowDays=7` 이므로 **직전 주 보고서만** 창에 든다.
정답으로 쓰는 그 주의 보고서는 입력에 **절대 넣지 않았다.** 이는 실제 운영과도 일치한다 —
서비스가 t 시점에 볼 수 있는 최신 NIFS 보고서는 언제나 지난주 것이다.

### 1.5 Granularity 불일치 (중요)

**정답은 "주 × 시군구" 광역 단위이고, 예측은 "해변 × 시점" 단위다. 이 둘은 결이 다르다.**
억지로 맞추지 않고 다음과 같이 처리했으며, 그 대가를 명시한다.

- 평가 단위를 **주 × 시군구(제주시/서귀포시)** 로 내렸다. 시군구 내 해변들의 **최대 점수/최대 단계**로 집계했다(안전 측 = 경보 누락을 벌하는 방향).
- **대가**: 해변별 변별력(협재 vs 함덕)은 이 백테스트로 **전혀 검증되지 않는다.** 정답에 해변 단위 정보가 없기 때문이다. `BEACH_VULNERABILITY`, `WIND_INFLOW`(해변 방위각 의존)의 해변 간 차이는 검증 불가다.
- 표본 = 68주 × 2시군구 = **136** (고밀도 26 / 저밀도 39 / 없음 71).

### 2.6 ★ 실제 배포 상태(v1-as-run)는 danger 를 낼 수 없다

**이것이 이번 백테스트의 가장 중요한 발견이다.**

[`nifs-report.parser.ts:152-153`](../src/contexts/observation/adapter/out/collector/nifs-report.parser.ts) 은 주간보고에 좌표가 없으므로 `lat: null, lng: null` 로 출현 레코드를 만든다.
그런데 [`risk-input.kysely-query.ts`](../src/contexts/risk/adapter/out/persistence/risk-input.kysely-query.ts) 의
`countNearbyAlerts` / `countPastSeasonOccurrences` 는 둘 다 `j.lat IS NOT NULL AND j.lng IS NOT NULL` 로 거른다.

→ **실데이터에서 `NEARBY_ALERT` 와 `PAST_OCCURRENCE` 는 절대 발화하지 않는다.**
(좌표가 붙는 건 `mock-collector.adapter.ts` 가 생성한 가짜 출현뿐이다.)

두 룰이 죽으면 관측만으로 도달 가능한 최대 점수는:

```
TEMP_UP 10 + TEMP_7D_AVG 5 + WAVE_HIGH 10 + WIND_INFLOW 10 + BEACH_VULNERABILITY 5 = 40
(+ CURRENT_INFLOW 10 은 전 기간 결측이라 실제로는 켜지지 않는다)
```

**40점 = caution 구간의 한복판이다. 시민 제보가 없는 한 danger(56+)/severe(76+)는 수학적으로 도달 불가능하다.**
백테스트의 v1-as-run 점수 범위가 정확히 **5~40** 으로 나온 것이 이 산수를 확인해 준다.

> ⚠️ `BEACH_VULNERABILITY` 는 해변의 취약도 값(5~20)이 아니라 **룰 점수(5)를 그대로** 더한다.
> `risk-assessment.ts` 는 `beach.vulnerabilityScore > 0` 인지만 보고 `mkVariable('BEACH_VULNERABILITY', ...)` 를 넣는다.
> → 12개 해변 전부에 붙는 **상수 오프셋**이고, 해변을 전혀 가르지 못한다. (이 문서의 초판은 여기를 20점으로 잘못 셈했다.)

백테스트가 이를 그대로 확인한다:

| 변형 | 점수 범위 | 단계 분포 | AUC | danger 이상 재현율 |
|---|---|---|---|---|
| v1 (버그 고쳤다고 가정) | 5~70 | safe 96 / caution 36 / danger 4 / severe 0 | 0.783 | 11.5% |
| **v1-as-run (실제 배포)** | **5~40** | **safe 129 / caution 7 / danger 0 / severe 0** | **0.653** | **0.0%** |
| v2 (제안, in-sample) | 5~75 | safe 99 / caution 17 / danger 20 / severe 0 | **0.868** | 57.7% |

실제 배포 상태는 136개 평가 단위 중 **129개(94.9%)를 "안전"이라고 답한다.** 고밀도 출현 26주 중 caution 이상으로 올린 것은 2주뿐이다.

## 3. 점수표 수정 제안

### 3.1 즉시 고쳐야 할 것 (버그)

1. **`NEARBY_ALERT` / `PAST_OCCURRENCE` 의 좌표 의존을 없애라.** (최우선)
   NIFS 주간보고는 시군구 단위이고 좌표를 주지 않는다. 그런데 두 카운트 쿼리가 좌표 필수다.
   → 좌표가 있으면 반경 매칭, **없으면 `beaches.region = jellyfish_occurrences.region` 으로 폴백**하도록 `countNearbyAlerts`/`countPastSeasonOccurrences` 를 고쳐야 한다.
   이걸 고치지 않으면 아래 점수 조정은 전부 무의미하다 — 룰이 켜지질 않으니까.
   *(주: `risk-input.port.ts` 주석은 "region 매칭은 제주시 해변 8곳이 전부 같은 점수를 받아서 좌표 거리로 바꿨다"고 적고 있다. 문제 인식은 맞지만, **좌표가 없는 유일한 실데이터 소스를 통째로 버리는** 부작용이 확인되지 않았다. 해변별 변별력은 다른 룰로 만들어야 한다.)*

2. **`severe` 도달 경로를 점검하라.** 관측만으로는 severe 가 영원히 불가능하다(최대 70점, v2 에서도 75점).

### 3.2 점수 재배분 제안 (v2)

| 룰 | 현행 | 제안 | 근거 |
|---|---|---|---|
| NEARBY_ALERT | 15 | **40** | 리프트 12.7, 단일 AUC 0.819. **압도적 최강 신호인데 과소평가돼 있었다** |
| TEMP_UP | 10 | **15** | 리프트 1.93, p<0.001 |
| TEMP_7D_AVG | 5 | **10** | 리프트 1.86, p=0.003 |
| PAST_OCCURRENCE | 15 | **5** | 리프트 1.28, p=0.31 — 유의하지 않다. 15점은 과대평가 |
| **WAVE_HIGH** | 10 | **0 (제거)** | 리프트 0.67 — 고밀도 주에 **오히려 덜** 켜진다. 노이즈 |
| **WIND_INFLOW** | 10 | **0 (제거)** | 리프트 0.93, p=0.77 — 무신호 |
| BEACH_VULNERABILITY | 5 | 5 (유지) | 광역 라벨로 검증 불가. 항상 켜지므로 순위에 영향 없음 |
| CURRENT_INFLOW | 10 | 10 (보류) | 검증 불가. 데이터가 생기면 재평가 |

**단계 구간**: `danger` 를 **56 → 40 부근**으로 내려야 한다(v2 점수 기준 danger 이상 재현율 57.7%, 오경보율 4.5%).

v2 결과 (in-sample): **AUC 0.868**, danger 이상 F1 **0.65** (현행 0.20), 균형정확도 **76.6%** (현행 55.3%).
직전주 NIFS 베이스라인(0.823)을 **처음으로** 넘어선다.

> ⚠️ **v2 가중치는 같은 136개 표본에서 뽑은 in-sample 값이다.** 별도 검증 표본으로 확인되지 않았다.
> "AUC 0.868" 을 성능 보증으로 인용하지 마라. 방향(무엇을 올리고 무엇을 빼야 하는가)만 근거가 있다.

### 3.3 근본 문제

`NEARBY_ALERT` 를 제대로 켜서 40점을 주면 점수표는 사실상 **"NIFS 지속성 예측기 + 수온 보정"** 이 된다.
그건 나쁜 게 아니다 — 실제로 그게 가장 잘 맞는다. 다만 **정직하게 그렇게 말해야 한다.**
"8개 요인을 종합한 위험도"라고 홍보하면서 실제로는 7개가 무의미하다면 그건 심사에서 뚫린다.

**해변별 변별력은 현재 어떤 룰도 만들어내지 못하고 있으며, 이 백테스트로는 검증할 수도 없다**(정답이 광역 단위라서).
해변 단위 예측을 주장하려면 해변 단위 정답 데이터(현장 관찰 일지, 안전요원 기록)가 필요하다.

## 4. 한계 — 이 백테스트가 말하지 못하는 것

1. **granularity 불일치.** 정답은 시군구(제주시/서귀포시) 주간 단위. 예측은 해변 시점 단위.
   → **해변별 위험도 차이는 전혀 검증되지 않았다.** 서비스의 핵심 주장인데 검증 수단이 없다.
2. **표본이 작다.** 136 단위, 그중 고밀도 26. 룰별 p 값은 다중비교 보정이 없고, 2026 홀드아웃은 20개뿐이다.
   → 룰 간 미세한 순위 차이(예: TEMP_UP vs TEMP_7D_AVG)는 **결론 내릴 수 없다.**
3. **계절 편향.** NIFS 주간보고는 **5~12월에만** 나온다(1~4월 0건). 겨울/봄 성능은 **완전히 미검증**이다.
4. **제보 룰 전부 검증 불가.** `REPORT_GENERAL/MULTIPLE/TOXIC/TOXIC_MULTIPLE/STING`, `MIN_TOXIC_1/HIGH/STING` —
   과거 시민 제보 데이터가 존재하지 않는다(서비스 미출시). **점수표의 5개 룰 + 3개 최소단계 보장은 여전히 완전한 잠정치다.**
   특히 `REPORT_STING +40`, `REPORT_TOXIC_MULTIPLE +35` 같은 큰 점수는 **아무 근거가 없다.**
5. **`CURRENT_INFLOW` 검증 불가.** KMA 는 유향·유속 미관측, KHOA(중문 TW_0075)는 과거 조회 API 없음 → 전 기간 결측.
6. **PDF 12건 파싱 실패**, 그중 대부분이 2024년 5~6월에 몰려 있다 → 초기 구간이 과소대표.
7. **PAST_OCCURRENCE 의 구조적 불이익.** 데이터가 2024-05 부터라 2024년 주간에는 "과거 연도" 자체가 없어 항상 0이다. 이 룰은 실질적으로 2025~2026 구간에서만 평가됐다.
8. **관측 표본이 하루 1회(12:00 KST).** 프로덕션은 30분 주기로 수집한다. 일중 변동(특히 파고)이 평활화됐다 → `WAVE_HIGH` 의 발화율이 실제보다 낮게 잡혔을 수 있다. 다만 리프트가 **역방향(0.67)** 이라 표본 밀도를 높인다고 신호가 생길 것 같지는 않다.
9. **관측소 매핑 단순화.** 프로덕션은 유형별 후보 2곳 중 `observed_at` 최신 행을 고르지만, 백테스트는 표본 시각이 동일하므로 **최근접 지점 우선, 없으면 차순위**로 단순화했다. `mergeObservations` 로직은 어댑터 private 함수라 스크립트에 복제했다.
10. **KHOA 부이(중문)를 매핑에서 제외**했다. 프로덕션에서는 중문색달의 최근접 marine 관측소가 KHOA TW_0075 지만, 과거 조회가 불가능해 KMA 중문 파고부이로 대체했다.

## 5. v2 확정 — §3 의 제안 중 무엇이 뒤집혔나

**§3 의 제안은 "룰별 단일 신호(리프트·p값)" 만 보고 쓴 것이다.** 그걸 그대로 점수표로 옮기기 전에,
**후보 점수표를 실제로 만들어 엔진에 넣고 비교**했다(스크립트 과제 E ~ E-6). 두 가지가 뒤집혔다.

전체 결정 과정·최종 점수표·한계는 **[`risk-rules-v2.md`](./risk-rules-v2.md)** 에 있다. 여기서는 결과만 요약한다.

### 5.1 뒤집힌 것 ① — 파고·풍향은 **제거하지 않는다** (10 → 5)

§3 은 "리프트 0.67 / 0.93 → 제거" 라고 썼다. **절제 실험(16개 조합 + 짝지은 부트스트랩 3,000회)이 그걸 뒤집었다.**

```
(d) v2-keep5 − (c) v2-drop:  ΔAUC 평균 +0.0072  CI[-0.010, +0.025]
                             Δdanger+재현율   CI[0.0%, 0.0%]   ← 완전히 동일
                             Δdanger+오경보율 CI[0.0%, 0.0%]   ← 완전히 동일
```

- **danger 단계에서 파고·풍향은 아무 일도 하지 않는다.** 0 이든 15 든 재현율 57.7% / 오경보율 0.0% / F1 0.65 로 **똑같다.**
  → "빼면 나빠지는가?" 의 답이 **"아니오"** 인 것처럼, "남기면 나빠지는가?" 의 답도 **"아니오"** 다.
- **caution 단계에서는 남기는 쪽이 낫다.** 고밀도 출현 주인데 "안전"이라 답한 건수가 **6건 → 4건**(26주 중)으로 준다.
  대가는 출현 없는 주의 caution 오경보 7.0% → 14.1%. caution 은 "모니터링 강화" 라 공개 경보가 아니다 — 남는 장사다.
- **왜 5 이고 10 이 아닌가**: 10 이면 관측만으로 도달 가능한 최대가 **65점 = danger** 가 된다.
  신호가 없다고 측정된 룰들로 해파리 근거 0인 날에 '위험'을 선언하는 경로가 열린다. **5 가 구조 제약의 상한이다.**
- 그리고 파고·풍향은 기상청 해상예보가 24h/72h 를 재평가하는 **유일한 입구**다(`FORECAST_BACKED_CODES`).
  0 으로 만들면 예보 연동이 통째로 죽는다. 성능 손실이 0 으로 측정된 이상 죽일 이유가 없다.

### 5.2 뒤집힌 것 ② — `NEARBY_ALERT` 는 40 이지, 그 이상은 안 된다

§3 은 "40" 을 제안했는데 근거가 없었다(리프트가 크니 크게, 정도). **NEARBY 를 스윕해 보니 40 이 상한이었다.**

| NEARBY | danger+ 재현율 | danger+ F1 | **severe 건수** |
|---|---|---|---|
| **40 (채택)** | 57.7% | 0.65 | **5 (3.7%)** |
| 45 | 61.5% | 0.68 | 14 (10.3%) |
| 55 | **69.2%** | **0.72** | **18 (13.2%)** ❌ |

**NEARBY ≥ 51 이어야 베이스라인의 재현율(69.2%)에 닿는다**(NEARBY + 취약도 5 ≥ 56).
**그런데 그 순간 severe 가 18건(13%)으로 폭발한다.** severe 는 대응 권고상 "구역 폐쇄 검토 / 입수 통제" 다.
136주 중 18주에 입수 통제를 권고하는 시스템은 아무도 안 믿는다.
(같은 기간 NIFS 자신이 특보를 낸 것은 136 단위 중 **6건(4.4%)** 뿐이다. v2 의 severe 3.7% 는 그 눈금과 맞다.)

**고정 구간(31/56/76)에서 다음 셋은 동시에 성립할 수 없다** — 산수다:
(i) NIFS 속보 하나로 danger 도달(NEARBY ≥ 51) · (ii) 관측만으로 caution 도달(관측 합 ≥ 31) · (iii) severe 로 안 튐(합 < 76).
(i)+(ii) ⇒ 합 ≥ 82 > 76 ⇒ (iii) 위반. **v2 는 (i)을 포기했다.**

### 5.3 최종 성능 (in-sample, 136 표본, 고정 구간 danger=56)

| 후보 | AUC | danger+ 재현율 | danger+ 오경보율<sup>†</sup> | danger+ F1 | caution+ 재현율 | **고밀도인데 "안전"** |
|---|---|---|---|---|---|---|
| (a) v1 현행 | 0.783 | 11.5% | 0.0% | 0.20 | 65.4% | **9건** / 26 |
| (b) 베이스라인 (지난주 NIFS 복사) | 0.823 | **69.2%** | 0.0% | **0.72** | 69.2% | 8건 / 26 |
| (c) v2-drop (파고·풍향 제거) | 0.868 | 57.7% | 0.0% | 0.65 | 76.9% | 6건 / 26 |
| **★ v2 채택 (파고·풍향 5점 유지)** | **0.875** | 57.7% | **0.0%** | 0.65 | **84.6%** | **4건** / 26 |

<sup>†</sup> 오경보율 = **출현이 전혀 없던 주**(n=71)에 danger 이상을 낸 비율. 저밀도 주의 경보는 헛경보로 세지 않는다(해파리는 실제로 있었다).

- `ΔAUC(v2 − v1) = +0.093`, 95% CI **[+0.040, +0.155]** — 0 을 포함하지 않는다. v1 이 나쁘다는 건 확실하다.
- **`danger` 재현율에서는 여전히 무지성 베이스라인에 진다(57.7% vs 69.2%).** 고정 구간이 강요한 대가다.
  **`danger` 컷오프를 56 → 45 로 내리면 재현율 69.2% / 오경보율 0.0% / F1 0.71 로 베이스라인과 같아진다.**
  그건 `src/shared/kernel/risk-level.ts` 수정이 필요해 이번 개정에 넣지 않았다 — **가장 값이 큰 후속 작업이다.**
- v2 가 베이스라인을 이기는 지점: 순위(AUC 0.875 vs 0.823), **경고 도달률(84.6% vs 69.2%)**,
  그리고 베이스라인이 **아예 못 하는 것**(해변별 차이 / 시민 제보 / 24h·72h 예보 / NIFS 공백기).

### 5.4 스크립트가 확장된 부분

- **엔진 등가성 검증**: `RiskEngine.calculate` 점수 == `Σ 점수표[발화 코드]` 를 **816건 전수 대조**한다(816/816 일치).
  룰의 발화 여부는 점수표와 무관하므로(임계값은 `THRESHOLDS` 에만 있다) 이 등가성 덕에 5,184개 조합을 초 단위로 탐색할 수 있다.
  **하나라도 어긋나면 스크립트가 즉시 throw 한다** — 탐색 결과가 실제 엔진과 다른 것을 재는 사고를 막는다.
- **짝지은 부트스트랩**: 두 점수표의 성능 **차이**에 95% CI 를 붙인다(같은 단위를 복원추출 → 표본 변동이 양쪽에 똑같이 걸린다).
- **그리드 탐색**: F2 목적함수 + 오경보 제약 + 구조 제약(관측만으로 danger 불가).
- **컷오프 스윕**: 구간을 옮길 수 있다면 얼마나 좋아지는지(= src 수정의 가치).

## 6. 재현 방법

```bash
cd Backend
npx ts-node --transpile-only -r tsconfig-paths/register scripts/backtest-risk.ts

# 캐시가 이미 있으면 (네트워크 호출 없이 수 초)
BACKTEST_NO_FETCH=1 npx ts-node --transpile-only -r tsconfig-paths/register scripts/backtest-risk.ts
```

- 외부 API 응답(주간보고 PDF 텍스트 80건, 기상청 관측 5,796건)은 **`os.tmpdir()/jellysafe-backtest`** 에 캐시된다.
  저장소 바깥이므로 **PDF 는 커밋되지 않는다.** 첫 실행은 약 10분(API 호출), 이후 재실행은 수 초.
- `BACKTEST_CACHE_DIR` 로 캐시 경로, `BACKTEST_NO_FETCH=1` 로 캐시 전용 실행(네트워크 차단)을 지정할 수 있다.
- 결과 상세는 `<cache>/backtest-result.json` 에 덤프된다(주별 정답·예측·요인 전량).

> 스크립트는 `Backend/src/**` 를 **읽고 import 만** 한다. 프로덕션 코드는 한 줄도 수정하지 않았다.
> 점수표 상수(`BEACHES`, `STATIONS`, `COLLECT`)는 `prisma/seed.ts` / `calculate-risk.service.ts` 에서 복제한 것이므로,
> 원본이 바뀌면 스크립트 상단 상수도 함께 고쳐야 한다.

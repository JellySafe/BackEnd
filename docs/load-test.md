# 부하 실측 (첫 기준선)

이 서비스는 그동안 **한 번도 부하를 재본 적이 없었다.** 그런데 트래픽이 몰리는 순간과 서비스가
가장 필요한 순간이 정확히 겹친다 — 성수기 낮 시간, 그리고 사고가 났을 때다. 그때 느려지거나
죽으면 "안전 정보를 제공한다" 는 목적 자체가 무너진다.

실행: `npm run load:test` (스크립트: `scripts/load-test.ts`)

## 1. 측정 조건

| 항목 | 값 |
|---|---|
| 대상 | Docker 컨테이너(`node:22-slim`, 비 root), 개발 노트북 |
| DB | 같은 노트북의 MySQL 8 컨테이너(tmpfs) |
| 시나리오 | `GET /public/beaches` 6 : `GET /public/beaches/:id/risk` 3 : `GET /health` 1 |
| 데이터 | 시드 상태(해변 12곳), 위험도 1회 산출 |

⚠️ **운영 환경이 아니다.** 운영은 `shared-cpu-1x / 512MB`(fly.toml)로 이 측정 환경보다 약하고,
관리형 MySQL 은 다른 리전에 있어 왕복 지연이 더 붙는다. **아래 수치는 상한으로 읽어야 한다.**
→ 운영 사양(1 vCPU/512MB)으로 다시 잰 결과는 **§8** 에 있다.

## 2. 결과

| 동시 | 처리량 | p50 | p95 | p99 | 최대 | 실패 |
|---|---|---|---|---|---|---|
| 20 | 555 req/s | 25ms | 77ms | 97ms | 373ms | 0 |
| 100 | 601 req/s | 86ms | **423ms** | 494ms | 1,136ms | 0 |

### 읽는 법

**동시성을 5배 올렸는데 처리량은 8% 늘고 지연만 5.5배가 됐다.** 이미 천장에 닿았다는 신호다.
그 지점을 넘긴 부하는 더 많은 사람을 처리하는 데 쓰이지 않고 **대기열에서 기다리게 만들 뿐이다.**

천장은 대략 **570 req/s** 근처다. 앱 화면 하나를 여는 데 API 를 5회쯤 부르므로,
**동시에 화면을 여는 사람 기준 초당 110명 남짓**이 지금의 한 대 용량이다.

좋은 신호도 있다. **실패가 0 이다.** 포화 상태에서 죽거나 오류를 뱉는 대신 느려지기만 했다 —
안전 서비스에서 중요한 성질이다(느린 응답은 늦게라도 닿지만, 5xx 는 아무것도 남기지 않는다).

## 3. 첫 실행에서 바로 드러난 것

처음 돌렸을 때 **요청의 89%가 429** 였다. 부하가 한 IP 에서 오니 기본 한도(300회/분/IP)에
즉시 걸린 것이다. 리밋은 의도대로 동작했지만, 그 상태로는 재는 것이 앱이 아니라 리밋이다.

그런데 그 한도가 **코드 상수라 바꿀 수 없었다.** 두 가지가 문제였다.

1. **부하를 잴 수 없다** — 위 이유.
2. **급증 때 손댈 수 없다.** 성수기 주말이나 사고 직후처럼 정상 트래픽이 몰려 실제 사용자가
   429 를 받기 시작하면, 코드를 고쳐 배포해야 푼다. **안전 정보를 막고 있는 상태에서 배포를
   기다리는 것**은 받아들이기 어렵다.

그래서 한도를 설정으로 뺐다(`RATE_LIMIT_DEFAULT_PER_MIN` 등). 기본값은 그대로라 아무것도
설정하지 않은 환경의 동작은 바뀌지 않는다.

## 4. 다음에 할 일

측정으로 근거가 생겼으므로 순서를 정할 수 있다.

1. ~~**운영 사양에서 다시 잰다.**~~ → 쟀다. §8 참고(1 vCPU/512MB 에서 **1,300~1,400 req/s**,
   병목은 **CPU**, 메모리는 23%). 관리형 MySQL 을 다른 리전에 두는 조건은 아직 못 재봤다.
2. ~~**공개 조회 캐시.**~~ → 넣었다. §6 참고(혼합 시나리오 기준 3.1~3.4배).
3. ~~**병목 지목.**~~ → 갈랐다. §5 참고(**DB 왕복**이었다).
4. ~~**부하 생성기 분산.**~~ → **필요 없어졌다.** 노트북에서는 천장이 생성기로 옮겨 갔지만
   (§6), 운영 사양에서는 **서버 CPU 가 91% 로 먼저 포화한다**(§8). 재고 있는 것이 서버가
   맞으므로 생성기를 나눌 이유가 없다. 노트북 상한을 더 높이는 것은 운영상 의미가 없다.
4. **머신 증설.** 그 전에 레이트 리밋 스토리지를 공유 저장소로 옮겨야 한다(README 후속 작업).

## 5. 병목은 어디였나 (경로별 측정)

섞어서 재면 "느리다" 까지만 알 수 있다. 한 경로씩 따로 재야 어디가 느린지 나온다
(`LOAD_PATHS` 로 경로를 지정한다).

| 경로 | 처리량 | p95 | 무엇을 하는가 |
|---|---|---|---|
| `/api/health` | **2,453 req/s** | 15ms | DB 를 타지 않는다 |
| `/api/public/beaches` | 804 req/s | 38ms | 해변 목록 + 최신 위험도 집계 |
| `/api/public/beaches/:id/risk` | 362 req/s | 73ms | 지평별 카드 + 원인 태그 |

**프레임워크는 2,453 req/s 를 낸다. 깎아먹는 것은 DB 질의다**(3~7배).
병목이 Node 단일 프로세스가 아니라 **DB 왕복**이라는 뜻이고, 그래서 캐시가 듣는다.
(반대였다면 캐시는 거의 효과가 없고 프로세스를 늘려야 했다)

## 6. 캐시를 넣고 다시 쟀다

`PUBLIC_CACHE_TTL_SECONDS`(기본 30) 적용 후 같은 조건에서 재측정했다.

### 경로별

| 경로 | 캐시 전 | 캐시 후 | 배수 |
|---|---|---|---|
| 해변 목록 | 804 req/s, p95 38ms | **2,047 req/s, p95 18ms** | 2.5× |
| 위험도 상세 | 362 req/s, p95 73ms | **2,143 req/s, p95 17ms** | 5.9× |

둘 다 DB 를 타지 않는 경로의 상한(2,453)에 가까워졌다. **병목이 DB 였다는 진단이 맞았다는
뜻**이다 — 캐시로 그 왕복을 없애자 프레임워크 한계까지 올라갔다.

### 혼합 시나리오 (§2 와 같은 조건)

| 동시 | 캐시 전 | 캐시 후 | 배수 |
|---|---|---|---|
| 20 | 555 req/s, p95 77ms | **1,866 req/s, p95 21ms** | 3.4× |
| 100 | 601 req/s, p95 423ms | **1,853 req/s, p95 80ms** | 3.1× |

⚠️ 20 과 100 의 처리량이 거의 같다(1,866 vs 1,853). 단일 경로 측정에서 서버가 2,143 을
냈으므로, 이 구간의 천장은 서버가 아니라 **부하 생성기**(단일 Node 프로세스)일 가능성이 크다.
더 큰 수치를 주장하려면 생성기를 여러 프로세스로 나눠 다시 재야 한다.

### 신선도는 TTL 이 아니라 무효화가 지킨다

캐시에서 가장 중요한 것은 처리량이 아니라 **낡은 위험도를 보여주지 않는 것**이다.
실제 컨테이너로 확인했다.

```
1) 첫 조회        generatedAt=2026-08-29T08:05:00.000Z
2) 재조회(캐시)    generatedAt=2026-08-29T08:05:00.000Z   ← 적중, DB 안 감
3) 재산출 트리거   POST /system/risk/calculate → 201
4) 재조회         generatedAt=2026-08-29T08:14:03.000Z   ← 즉시 새 값
```

TTL(30초)을 기다리지 않는다. 산출이 끝나면 캐시를 비우기 때문이다. 제보 검수(ADM-009)가
부르는 단건 재산출도 같은 경로를 지나므로, **검수 직후 시민은 바뀐 위험도를 바로 본다.**

⚠️ 캐시하는 경로는 **허용 목록으로 좁혀 둔다.** 관심 해변·알림함처럼 소유자가 있는 응답이
섞이면 남의 자료가 다른 사람에게 보인다. 자격증명이 실린 요청도 캐시하지 않는다 —
지금은 응답이 같지만 나중에 개인화가 붙는 순간 사고가 되기 때문이다.

## 7. 스크립트가 재지 않는 것

- **서버 쪽 상태.** 부하를 만드는 쪽만 본다. 그때 서버가 어땠는지는 `GET /system/metrics`
  (신선도·적체)와 DB 커넥션 수를 함께 봐야 한다. 한쪽만 보고 "괜찮다" 고 판단하지 않는다.
- **쓰기 경로.** 제보 접수·이미지 업로드는 넣지 않았다. 과금·디스크·AI 판별 큐가 얽혀 있어
  부하 스크립트로 쏘면 부작용이 크다. 그쪽은 따로 설계해야 한다.
- **운영 환경.** 공개 조회라도 레이트 리밋과 DB 부하는 실제 사용자에게 간다. 운영에 쏘지 않는다.

## 8. 운영 사양에서 다시 쟀다 (§4-1 완료)

§2 의 수치는 개발 노트북 상한이었다. 운영은 `shared-cpu-1x / 512MB`(fly.toml)이므로,
컨테이너를 **1 vCPU / 512MB 로 묶고** 같은 시나리오를 다시 걸었다.

```
docker run --cpus=1 --memory=512m -e NODE_ENV=production ...
```

### 결과

| 동시 | 처리량 | p50 | p95 | p99 | 최대 | 실패 |
|---|---|---|---|---|---|---|
| 20 | 1,272 req/s | 11ms | 38ms | 86ms | 381ms | 0 |
| **50** | **1,391 req/s** | 27ms | 84ms | 139ms | 1,446ms | 0 |
| 100 | 1,313 req/s | 54ms | **145ms** | 264ms | 3,550ms | 0 |

### 자원 사용

| | CPU | 메모리 |
|---|---|---|
| 유휴 | 0% | 103MB |
| 동시 50 부하 중 | **91%** | 118MB (**23%**) |

### 읽는 법

**천장은 1,300~1,400 req/s 근처이고, 동시 50 이 가장 좋은 지점이다.** 거기서 100 으로
올리면 처리량은 늘지 않고 지연만 커진다 — 그 위의 부하는 더 많은 사람을 처리하는 데 쓰이지
않고 대기열에서 기다리게 만든다.

**어느 수준에서도 실패가 0 이다.** 포화 상태에서 죽거나 5xx 를 뱉는 대신 느려지기만 했다.
안전 서비스에서 중요한 성질이다 — 느린 응답은 늦게라도 닿지만, 5xx 는 아무것도 남기지 않는다.

**병목은 CPU 다. 메모리가 아니다.** 부하 중에도 512MB 중 23%(118MB)만 쓴다. 즉 **메모리를
키우는 증설은 이 서비스에 아무 효과가 없고**, 늘려야 하는 것은 CPU 또는 머신 수다.
비용을 쓸 곳을 정할 때 이 구분이 중요하다.

노트북(§2 캐시 적용 후 혼합 기준)의 대략 4분의 3 수준이다. 예상보다 잘 나왔는데, 공개 조회가
대부분 캐시에서 나가 CPU 만 쓰기 때문이다.

### ⚠️ 이 수치를 그대로 믿으면 안 되는 이유

측정 조건이 운영과 다른 부분을 남겨 둔다. **아래 넷은 전부 실제 운영을 더 낮게 만든다.**

1. **`--cpus=1` 은 전용 코어 하나다.** Fly 의 `shared-cpu-1x` 는 **공유 슬라이스**라 이웃
   부하에 따라 훨씬 적게 받을 수 있다. 이 측정은 낙관적인 상한이다.
2. **DB 가 같은 호스트에 있다.** 관리형 MySQL 이 다른 리전에 있으면 질의마다 왕복 지연이
   붙는다. 캐시 적중률이 낮은 경로일수록 차이가 커진다.
3. **레이트 리밋을 열고 쟀다**(`RATE_LIMIT_DEFAULT_PER_MIN` 을 크게). 서버 용량을 보려는
   측정이라 그렇게 했다. 실제로는 IP 당 분당 300회가 걸린다 — 아래 참고.
4. **Docker Desktop(Windows)의 포트 포워딩이 끼어 있다.** 이건 실제로 측정을 한 번 망쳤다
   (아래).

### 잘못 읽을 뻔한 것 — 처리량이 떨어진 줄 알았다

동시 100 첫 측정에서 **818 req/s, 실패 100건**이 나왔다. 동시 50 보다 낮아서 "포화를 넘겨
무너진다" 고 읽을 뻔했다.

컨테이너 **안에서** 부르면 정상이었다. 앞선 측정이 만든 수만 개의 연결이 호스트 쪽
포트 포워딩을 고갈시킨 것이었고, 서버는 멀쩡했다. 잠시 쉬었다가 다시 재니
**1,313 req/s, 실패 0건**이 나왔다.

교훈은 **부하 측정에서 실패를 보면 서버부터 의심하지 말 것**이다. 생성기와 서버 사이의
모든 것이 후보다. 안에서 한 번 불러 보는 것으로 갈렸다.

### 레이트 리밋이 먼저 걸린다 (기본 설정에서)

리밋을 열지 않고 그대로 쟀을 때는 이렇게 나왔다.

```
동시 20 / 30초 → 요청 34,995건 중 성공 3,812 / 429 31,183
```

**한 IP 에서 오는 부하는 서버 용량에 닿기 한참 전에 리밋에 막힌다.** 부하 스크립트였으니
설계대로 동작한 것이지만, 여기서 문제가 하나 드러났다 — 서버가 보기에 **이 스크립트와
"공용 와이파이 뒤에 200명" 은 구분되지 않는다.**

해수욕장 와이파이 한 대 뒤에 사람이 몰리는 상황은 이 서비스에서 드문 일이 아니고, 통신사
CGNAT 뒤에서는 모바일 이용자 수천 명이 한 IP 로 보인다. 그 전부가 **한 버킷(300회/분)을
나눠 쓰고 있었다.**

→ **고쳤다.** 기본 한도를 IP 가 아니라 **기기(신원)** 기준으로 세고, IP 는 남용을 막는
상한(`ip-ceiling`)으로만 쓴다. 근거와 수치는 `src/shared/http/rate-limit.config.ts`,
동작 확인은 `test/rate-limit.e2e-spec.ts`(같은 IP·다른 기기가 서로를 밀어내지 않는지).

### 그래서 몇 명을 감당하나

앱 화면 하나를 여는 데 API 를 5회쯤 부른다. 1,300 req/s 이면 **동시에 화면을 여는 사람
기준 초당 260명** 남짓이다. 다만 위 1~2 번(공유 CPU·원격 DB) 때문에 실제 운영은 이보다
낮게 잡아야 하고, **절반 정도로 보수적으로 계획하는 편이 안전하다.**

### 여기서 나온 별건 — 이미지가 부팅하지 못했다

이 측정을 하려고 운영 이미지를 처음 띄웠을 때 **컨테이너가 곧바로 죽었다.** `pdf-parse` 가
`DOMMatrix is not defined` 로 터졌고, 원인은 선택적 네이티브 패키지(`@napi-rs/canvas`)의
바이너리가 이미지에 없었던 것이다. npm 은 **선택적 의존성 설치 실패를 조용히 넘기므로**
`npm ci` 는 성공으로 끝나고 이미지 빌드도 성공한다 — 그리고 그 이미지는 뜨지 못한다.

부하 측정을 하지 않았다면 드러나지 않았을 종류의 결함이다. 조치는 별도로 했다
(`nifs-jellyfish.collector.ts` — PDF 파서를 쓸 때 불러오도록 바꿔, 그 자료원 하나만 실패하고
서비스는 뜨게 했다).
